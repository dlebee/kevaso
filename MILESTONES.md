# Milestones

> The order below is the proposal we agreed to start with. It sets the build order only and can change
> at any time; the design (in the private idealization repo) is the scope.

Every milestone ends with **green unit tests** for what it adds, and from M3 on with an end-to-end run of
the test loop (create machines → `kvoadm` → test → tear down) on Lima locally and on GitHub's
`ubuntu-latest` runner in CI. Milestones set the build order only; everything in the design is in scope.

Unit-test style for every package (see `docs/adr/0001-testing.md`):
- logic as pure functions (`decide(desired, observed) → plan`), tested with tables;
- controllers against the in-memory store, fake clock and fake plugins; assert the **end state**;
- every fake plugin passes the same conformance suite as the real ones;
- `go test -race ./...` in CI, plus a goroutine-leak check.

## Where things are proven

| Place | What ran there | Caveat |
|---|---|---|
| In-process | every milestone's unit and integration tests; property, fuzz and golden tests | no real kernel, network or machine |
| Lima VMs | M3–M10's e2e loop; since the sealed model: `TestVMLeases`, `TestTerminalsAndUI`, `TestVMVolumes`, `TestVMMoves`, `TestSecretsInASilo` | no real external IP (Lima's network isn't routed); `TestMoves`, `TestApprovals`, `TestPanes`, `TestDaemonsAndUpkeep` ran before the sealed model |
| Real Linodes | M6 leases, M11, M14 JuiceFS and moves, M15 terminals, M16 HA and upgrades, M17 plugin operators | all **before the sealed model**; no KVM, so containers only |
| Bare metal | the one-machine suite, each test on one of two Ubuntu 26.04 machines: model, names, images, secrets (microVMs and containers), ingress with Let's Encrypt staging, probes, leases, panes, fencing, volumes, private registry, podman, reboot | **one machine at a time** so far |

**Not proven anywhere:** two machines together on bare metal; the failure cases; a soak; OpenShell on
bare metal; private networks between hosts (hosts with internal IPs on a shared network); NAT clouds
(an external IP on no interface).

## Parked until stabilization ends

- The JuiceFS provider's redesign (research D001).

- New providers.
- A macOS runtime.
- Volume retention.

## Awaiting the owner

Questions the bare-metal runs raised, not decided:

- A held ingress class (a refused annotation keeps its last good config) also holds back new routes
  for every other Ingress of the class.
- Local volume data doesn't move between hosts, so a microVM with a local volume is pinned to its host.
- Thin pools can overcommit, so a volume request larger than the pool has is not refused.
